## Decisions

### Next.js on Vercel

One TypeScript codebase covers the UI, server routes and server actions. The App Router supports server components and streaming, which suit AI responses. Vercel runs Next.js with no setup and handles preview deploys for each branch. Tailwind keeps styling in the markup and doesn't need a design system yet.

The scaffold uses Next.js 16. Two changes from older Next.js matter here: the middleware file is now `src/proxy.ts`, and `LayoutProps` / `PageProps` types are generated by `next typegen`. The `typecheck` script runs `next typegen` first for this reason.

### Web first, then PWA, then Expo

Adults will mostly plan and study on a laptop, and check in on a phone. The web app ships fastest and is easiest to iterate on. A PWA adds an install icon, offline shell and web push for check-ins (PRD F7, story 11) without a second codebase. We move to Expo (React Native) only when native features such as reliable notifications or widgets justify it. Expo lets us reuse TypeScript, the API and much of the logic. For that reason, business logic belongs in `src/lib` and server routes, not in React components.

### Postgres on Neon with Drizzle

Postgres is the one store for user data, plans, the mastery graph and later embeddings. Neon is serverless Postgres. It scales to zero, gives each preview deploy a database branch, and its HTTP driver works in serverless functions without connection-pool problems. Drizzle is a thin, typed query builder. Its schema is plain TypeScript, and it produces readable SQL migrations. It has no heavy runtime or code generator.

The schema has only a `users` table for now, keyed by the Clerk user id with created and updated timestamps. The domain model (goals, roadmap, topics, mastery, glossary) waits until we decide where content comes from (see Open decisions), because that choice shapes the topic tables.

- `pnpm db:generate` writes SQL migrations to `drizzle/` from `src/db/schema.ts`.
- `pnpm db:migrate` applies them. It uses `DATABASE_URL_UNPOOLED` if set, otherwise `DATABASE_URL`.

### Mastery graph as Postgres tables, not a graph database

The knowledge and mastery graph (PRD F2) will be modelled as ordinary tables: `topics`, `topic_edges` (prerequisite and related-to links), and per-user `mastery` rows. Reasons:

- The graph is small per user (hundreds to low thousands of nodes) and the queries are shallow: prerequisites of a topic, what's unlocked next, neighbours worth exploring. Recursive CTEs handle these.
- Mastery data has to join with plans, sessions, assessments and the glossary. Keeping it all in one transactional store avoids syncing two databases.
- A graph database adds a second system to run, back up and secure, with no clear benefit at this size.

We'll revisit this only if real queries need deep traversals that Postgres can't serve fast enough.

### pgvector later

When we need semantic search, such as matching a sidekick question to glossary terms or finding related topics and content, we add the pgvector extension to the same Neon database. Neon supports it. We won't add a separate vector database.

### FSRS for spaced review

Spaced review (PRD story 16) will use FSRS (Free Spaced Repetition Scheduler). It is open source and well studied, and it models per-item difficulty, stability and retrievability better than SM-2. The review state per user and item will live in Postgres next to the mastery rows. The scheduler is a pure function, so it can run in a background job or at request time.

### Clerk for auth

Clerk provides hosted sign-in and sign-up UI, sessions, social login and user management. We don't have to build or secure these ourselves. Clerk also has an Expo SDK, which fits the path to native apps.

Wiring:

- `src/proxy.ts` runs `clerkMiddleware()` so server code can read auth state.
- `<ClerkProvider>` sits inside `<body>` in the root layout.
- Sign-in and sign-up live at `/sign-in` and `/sign-up` as catch-all routes.
- `/app` is protected by `auth.protect()` in `src/app/app/layout.tsx`. This follows Clerk's current guidance: it has deprecated `createRouteMatcher` path matching in the proxy in favour of checks placed next to the resource.
- Clerk Core 3 (`@clerk/nextjs` 7) replaced `<SignedIn>` / `<SignedOut>` with `<Show when="signed-in" | "signed-out">`.

Clerk owns identity. Our `users` row holds only the Clerk id so that domain tables have a local foreign key. A Clerk `user.created` webhook (or lazy upsert on first request) will create the row. This is not built yet.

### PostHog for product analytics

The PRD defines leading indicators such as onboarding completion, week-1 session completion, return after a missed week and sidekick use. PostHog covers event analytics, funnels, retention, feature flags and session replay in one tool.

- `src/components/posthog-provider.tsx` initialises `posthog-js` on the client with a `defaults` config snapshot. The snapshot includes automatic `$pageview` capture on App Router navigations. The provider also links the anonymous id to the Clerk user id on sign-in and resets it on sign-out.
- `src/lib/posthog-server.ts` provides a `posthog-node` client for server-side events. It flushes right away because serverless functions can end before a batch is sent.
- If `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` is unset, analytics is off and the app still runs.

### Background jobs: Inngest or Trigger.dev (not yet installed)

Roadmap generation, replanning after missed sessions (PRD F7), scheduled check-ins and FSRS review scheduling are long-running or scheduled work. They don't fit in a request. Both Inngest and Trigger.dev offer durable, retryable steps and cron on Vercel. We'll pick one when the first job exists. The main factors are pricing and how each handles long LLM steps.

### LLM observability and evals

- **Tracing and cost:** Langfuse or PostHog LLM analytics, not yet chosen. PostHog is already in the stack, which favours it. Langfuse has richer prompt management and datasets. Either way, every AI call should log task type, model, tokens, latency, cost and which fallback (if any) served it.
- **Evals:** promptfoo, with one suite per task type. Evals are what gate the model allowlist (see below).

## AI router

All AI calls go through `src/lib/ai/`. Application code asks for a model by task type, never by model ID.

```
task type ──► TASK_ROUTES (tier, required capabilities, fallback tiers)
                  │
user prefs ───────┤  (limit providers, prefer cheaper, BYOK)
                  ▼
MODEL_REGISTRY ∩ MODEL_ALLOWLIST ──► resolveModel() ──► { primary, fallbacks[] }
                                                             │
                                               toLanguageModel() ──► AI SDK call
```

| File | Role |
|---|---|
| `models.ts` | Registry of known models: provider, tier (`fast` / `standard` / `deep`), capabilities (`structuredOutput`, `toolUse`, `contextWindow`), pricing, stable or preview. Also the allowlist. |
| `tasks.ts` | Route table. Each task type has a default tier, required capabilities and a fallback chain of tiers. |
| `router.ts` | `resolveModel(task, userPrefs)` returns the best eligible model and an ordered fallback list. |
| `providers.ts` | Turns a routed model into an AI SDK `LanguageModel`, using the BYOK key or the platform key. |
| `router.test.ts` | Vitest unit tests for the router. |

Task types: `sidekick_answer`, `glossary_define`, `goal_clarify`, `goal_discover`, `roadmap_generate`, `replan`, `assessment_grade`, `gap_detect`.

### Design principles

1. **Route by task type.** Tasks differ in the stakes, latency and output shape they need. A sidekick answer needs speed. A roadmap needs depth and structured output. Routing by task keeps those tradeoffs in one table that we can review and evaluate, instead of model IDs scattered through the code.
2. **User settings limit the choice, they don't override the router.** A user can restrict providers, ask for cheaper models or bring their own key. These narrow or reorder the candidates, but the router still applies the task's tier chain and hard requirements. A user can't force a fast model onto roadmap generation, for example. Specifically:
   - `allowedProviders` filters candidates.
   - `preferCheaper` reorders models within a tier by blended price. It never drops to a lower tier.
   - `byok` ranks that provider first within each tier and marks those calls as billed to the user's key. It doesn't change the tier.
3. **Eval-gated allowlist.** A model in the registry is not routable until it is on `MODEL_ALLOWLIST`. It gets there by passing the promptfoo suites for the tasks it can serve. Preview models stay off. Model upgrades become a data change backed by eval results.
4. **Fail loudly.** If no allowlisted model meets a task's requirements within the user's limits, `resolveModel` throws `NoEligibleModelError` and says why (empty allowlist, no model from the allowed providers, missing capability, or no model in the tier chain). It never quietly uses a model that can't do the job.
5. **Fallbacks are ordered.** The caller tries `primary`, then each entry in `fallbacks`, on provider errors or timeouts. The same chain works for outages and rate limits.

## Business model consequences

Decided in [business-model.md](business-model.md): a $20/month subscription with AI bundled, a 14-day trial with activity tracking, and BYOK later. What this means for the architecture (none of it is built yet):

- **AI usage metering.** Every AI call writes a row with user, task, model, `keySource`, tokens and cost. This feeds the per-user soft monthly limit, the cost-per-learner metric and, later, BYOK.
- **Router soft limit.** `resolveModel` will take the user's month-to-date spend. Above the limit it prefers cheaper tiers for tasks where evals show quality holds.
- **Entitlements.** A `subscriptions` or entitlements table holds the plan state: `trialing`, `extended`, `active`, `paused`, `keep_my_plan` or `canceled`. It also holds `trial_ends_at` and whether the one extension has been used.
- **Trial segmentation job.** A daily background job sorts trial users into segments on day 10 and day 14 and triggers the matching email or in-app message.
- **Billing.** Stripe, possibly through Clerk Billing. Not chosen yet.
- **BYOK.** The router already supports it. Encrypted key storage and the settings UI come later.

## Open decisions

These are under discussion now and will shape the next round of architecture work.

### Where content comes from

**Decided.** See [content.md](content.md). Content is a hybrid kept entirely in the app. Each subject area has a reviewed skill map, and lessons are written by AI and grounded in a stored source library. Launch areas: the California real estate exam, data analytics and AI at work. AI reviewer agents check content, and people review by exception. What changes here:

- **pgvector** moves from "later" to now, for the source library.
- **Background jobs** are needed now for the generation and review pipeline. Recommendation: Inngest.
- **LLM tracing** is required, not optional. Recommendation: Langfuse, linked to the Postgres review records by trace id.
- **Router:** add reviewer task types, a `mustDifferFrom` provider constraint so reviewers use a different provider from the generator, and a `goal_discover` task.
- **Domain schema:** the tables are listed in [content.md § Data model](content.md#data-model-to-build-next).
